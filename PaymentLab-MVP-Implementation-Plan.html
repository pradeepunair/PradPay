Release definition

One purchase. Three perspectives. One evidence trail.

The MVP is a public, portfolio-linked sandbox showing an agent-led USD sale from Buyer, Merchant, and PSP perspectives. Every view derives from the same persisted transaction evidence.

Mode boundary

Guided Replay is public, reliable, and read-only. It never invokes models, checkout mutations, payments, or webhooks. Live Sandbox uses bounded agents and may create one Stripe test-mode sale only after explicit, auditable authority.

Schedule rule. The phase sequence is committed; calendar estimates are not. Phase 0 must verify account capabilities, infrastructure, and ownership before dates are assigned.

Explicitly outside the MVP

Refunds, disputes, real fulfillment, real money, multi-PSP routing, PayPal fallback, marketplace payouts, subscriptions, production buyer identities, AP2 cryptographic mandates, and autonomous browser shopping.

  • Prove durable wait, retry, callback wake-up or polling, crash recovery, and one committed dispatch.

Component architecture

The database commit is the synchronization point.

Models propose actions through bounded tools. Server-side services own commerce truth. Every observer projection comes from persisted events—not model prose or browser state.

Hard authority boundaries

  • The browser can request and display; it cannot establish price truth, valid authority, or payment success.
  • Buyer and Merchant agents have separate prompts and tool allowlists even if they share a model.
  • ACP wire objects are validated against one pinned release; custom application behavior is labeled separately.
  • Stripe credentials and raw reusable payment tokens stay in trusted backend code.
  • Webhook input becomes trusted only after raw-body signature verification and durable receipt.

Guided Replay

Select a sanitized scenario → play, pause, step, rewind, or change speed → switch Buyer, Merchant, PSP, and All Views → inspect “what happened / why / evidence” → review the outcome. Historical cursor changes never reveal future facts and cannot invoke live mutations.

Live Sandbox

Create session → choose scenario and mission → confirm normalized requirements → agents compare and prepare checkout → grant exact or bounded authority → revalidate and reserve → submit once → verify or reconcile provider evidence → show an honest terminal or waiting state.

Interaction contract. Setup consent, purchase authority, provider authentication, payment submission, provider response, and verified confirmation are six distinct facts in the UI and data model.

Unknown outcome rule

A timeout preserves unknown, the original attempt, inventory reservation, and one-purchase authority. Recovery retrieves a known provider object or safely retries the same operation with the same idempotency key and payload. It never creates a new payment merely because a response was lost.

Immediate next move

Start with Phase 0—not application scaffolding.

The first working session should resolve the platform inventory and establish evidence for the riskiest integration boundary.

  1. Confirm the implementation and portfolio repositories and any local instructions.
  2. Verify Vercel scope, database/workflow availability, Stripe test mode, and model-provider constraints.
  3. Pin ACP artifacts and test exact schema/auth/capability behavior.
  4. Complete one small supported Stripe test payment and verified webhook callback.
  5. Accept ADRs 001–004 and choose integrated live, labeled extension, or replay-only continuation.
  6. Estimate Phases 1–5 from verified scope and available capacity.
Human control remains explicit. Phase 0 does not authorize publication, DNS edits, portfolio changes, real-money processing, or unrelated account mutations.
