PaymentLab AI — Agentic Checkout MVP

Product requirements and Codex implementation plan
Version 1.0 · 7 September 2026 · Owner: Pradeep Nair
Status: implementation-ready product specification; infrastructure identifiers and protocol compatibility spike remain to be verified.

1. Product brief

Build a public, portfolio-linked application that demonstrates a complete sandbox sale conducted by a Buyer Agent and a Merchant Agent. A visitor defines a shopping mission and purchasing authority, observes the agents choose a product and prepare checkout, and sees the resulting payment through Buyer, Merchant and PSP perspectives. All perspectives use the same persisted transaction evidence.

The portfolio objective is to demonstrate Pradeep's capability as an AI-enabled Payments Product Manager: product definition, agent-driven commerce, payment lifecycle correctness, consent boundaries, merchant economics, resilience and clear communication to payment experts who are not engineers.

Core question: Can a buyer delegate a purchase while retaining control over what is bought and how payment occurs, and can a merchant reliably accept that purchase?

Five-minute story: mission → product comparison → merchant quote → permission check → ACP checkout completion → Stripe test sale → verified payment evidence → receipt and run evaluation.

This document specifies a new demo; it does not assert that an app, repository, project, payment account or protocol integration has already been created.

3. Audience and product promise

Primary users: payments hiring managers, product leaders, solution architects and non-engineering payment specialists. Secondary users: engineers inspecting integration evidence and Pradeep presenting a live walkthrough.

A visitor should understand, without reading code:

  • Who is acting for the buyer and merchant.
  • Which purchase was permitted, when permission was given and why an action was allowed or blocked.
  • Which facts came from merchant tools versus agent interpretation.
  • What the processor actually confirmed and what remains uncertain.
  • How the application avoids repeating a sale after a lost response.
  • How product requirements, payment records and business outcomes connect.

The demo must distinguish application consent, provider authentication, issuer/payment authorization, capture, settlement and fulfillment. A successful test sale does not demonstrate actual settlement or delivery.

4. MVP scope and non-goals

Required for first public release

  1. One fictional merchant, six fictional headphone products, USD, quantity one per purchase and one synthetic US shipping profile.
  2. Buyer and Merchant LLM agents with separate prompts, tool permissions and bounded execution.
  3. Version-pinned ACP checkout implementation for the supported operations, with a documented payment-handler compatibility boundary.
  4. Two public demo options: Guided Replay and Live Sandbox.
  5. Three synchronized perspectives plus desktop All Views layout.
  6. Shopping mission, structured requirements, product comparison and evidence-based selection summary.
  7. Deterministic inventory, pricing, offer eligibility, illustrative tax/shipping and basic merchant risk rules.
  8. Explicit final-purchase approval and bounded one-purchase delegation, including expiry and revocation.
  9. Stripe test-mode sale using automatic capture, verified webhooks and durable state.
  10. Successful sale, consent block and uncertain-response recovery scenarios.
  11. Redacted technical evidence, event explanations, run metrics and an implementation case study.
  12. Session isolation, persistent limits, cleanup, operational diagnostics and a live-demo kill switch.
  13. Vercel deployment instructions and portfolio integration change.

Explicitly deferred

PayPal integration; multiple processors and real fallback; routing scores based on actual provider comparison; delayed capture and partial capture; void operations after authorization; refunds; returns; disputes; subscriptions; marketplace payouts; real inventory, shipping, tax and fulfillment; real money; production buyer identities; full multi-merchant discovery; AP2 cryptographic mandates; autonomous browser shopping; ChatGPT marketplace distribution; broad third-party agent onboarding.

Retain extension seams, but do not build empty agent services or claim these features work. In MVP, order details show “Refunds and disputes: planned for a later release.” PSP selection states “Stripe — sole enabled test provider,” without fabricated routing scores. Authorization and capture are shown only to the extent supported by returned payment evidence.

5. Public demo modes

5.1 Guided Replay

Purpose: instant, reliable exploration with no model or payment API cost per visitor.

  • Available without registration and the default portfolio entry.
  • Select one of the three recorded scenarios; play, pause, step, rewind, restart, seek and choose 0.5×/1×/2× speed.
  • Switch perspective or use All Views without restarting the recording.
  • Every recorded event supports an explanation and evidence drawer.
  • Prominent label: “Recorded sandbox run — no new payment is being made.”
  • Use sanitized, versioned recordings captured from actual integrated test runs for release. Before these exist, development fixtures must say “Synthetic development fixture,” never “recorded live run.”
  • Replay reconstructs snapshots from events at the selected cursor, including backward seeking. It must not show future decisions before their events occur.
  • Replay never invokes live agent, checkout, payment or webhook mutations. Use a separate read-only route and replay engine.
  • Do not replay credentials, reusable authorization tokens or full personal data. Preserve safe references or pseudonyms and relationships.
  • Capture actual timings; compressed playback must disclose that time is accelerated. Original latency remains visible separately.

5.2 Live Sandbox

Purpose: let visitors run actual LLM agents and actual Stripe test payments.

  • Anonymous, opaque session cookie; registration not required.
  • Select a bounded scenario, enter a mission up to 600 characters and review structured requirements.
  • Only the seeded merchant/catalog and synthetic profile are supported. Unsupported requests get an explanation, not a fabricated search result.
  • Test payment setup uses Stripe-hosted fields and documented test credentials. A clearly labeled synthetic test-instrument shortcut may be enabled only through a documented, supported test API path. Never silently substitute mock payment results.
  • Record explicit setup consent separately from purchase authority. No real card or personal shipping information is requested.
  • Show “Live agents · Stripe test mode · no real money moves” plus scenario-specific simulation labels.
  • Permission challenge pauses the workflow, not an open function call.
  • Closing or reloading the browser does not duplicate the transaction. Reconnect from persisted events.
  • Public views can be opened in separate windows for the same authorized session/run.
  • Live display can pause while processing continues; label “Display paused — processing continues.” Live rewind is inspection only, never transaction reversal.
  • At a usage limit or missing integration, offer Guided Replay with a clear reason. Never relabel replay as live.
  • Each scenario that charges requires its own one-purchase authority.

Default configurable budgets

Three new live runs per anonymous session per rolling 24 hours; one active run per session; a privacy-preserving secondary IP throttle; 100 new live runs per deployment per day; at most 12 model calls per run and two bounded offer exchanges; 15,000 input and 4,000 output tokens per run; 180 seconds of active agent work, excluding user waiting; 10-minute quote/reservation lifetime; 15-minute mandate maximum lifetime.

These are proposed product defaults, not platform limits. Implement persisted atomic counters and admission checks. Reserve estimated model budget before dispatch, settle against actual usage and leave headroom for in-flight calls. Stop agent planning when limits are reached, but continue reconciliation of any already-submitted payment. Provider billing and token reporting may differ; do not claim an exact spend hard cap unless supported by the provider.

6. Representative catalog and pricing rules

Use clearly fictional brand and product names and owned/generated/licensed images with attribution where needed. Seed at least six products: two qualifying candidates, one above budget, one with insufficient battery life, one with slow delivery and one unavailable. Store price, cost, stock and policies server-side.

Reference deterministic quote for fixture tests:

  • Product: $279.00; eligible demo offer: $10.00; merchandise after offer: $269.00.
  • Express shipping: $12.00.
  • Illustrative tax: 8.25% of discounted merchandise only, rounded once half-up to cents: $22.19.
  • Total: $303.19. Budget: $315.00. Remaining allowance: $11.81.
  • Illustrative cost of goods: $190.00. Shipping revenue and cost: both $12.00.
  • Illustrative processor assumption: 2.9% of total + $0.30 = $9.09 after half-up rounding. This is a demo assumption, not a quoted Stripe rate.
  • Estimated contribution: $269.00 + $12.00 − $190.00 − $12.00 − $9.09 = $69.91.
  • Contribution margin denominator is net merchandise plus shipping revenue, excluding tax: $281.00; margin approximately 24.88%.

Use integer minor units and integer basis points/rational arithmetic; never floating-point money. Show calculation assumptions in an expandable card. Tax is explicitly illustrative and must not claim jurisdictional correctness. Avoid hard-coded stale dates: use the run's reference time and the synthetic profile's timezone to resolve “Friday”; display the resolved calendar date for consent. Recorded runs retain their original clock.

Inventory is isolated per live run so strangers do not exhaust a shared fake store. Reservation version and expiry are still enforced to demonstrate actual concurrency controls. Reject checkout changes during a payment submission. Preserve reservation while payment outcome is unknown; reconcile before releasing it.

8. Agent contracts and business authority

Buyer Agent and Merchant Agent are separate roles even if using the same model. Persist agent/model/prompt versions for each run. Use structured outputs with server validation, a fixed tool allowlist and bounded iterations.

Buyer tools: searchCatalog, requestMerchantOffer, compareCandidates, createCheckout, updateCheckout, readCheckout, requestPermission, completeCheckout, getOrderStatus.

Merchant tools: readCatalog, checkStock, evaluateOffer, calculateQuote, reserveInventory, readCheckout, getOrderStatus.

All names above are internal proposed tools, not ACP-standard method names. Buyer checkout tools invoke the ACP client against merchant endpoints; do not bypass the protocol adapter in the live story. Merchant conversational replies wrap merchant-service results; they cannot overwrite those results.

Each tool checks run/session identity and agent role. Models never receive Stripe secret keys, bearer credentials, client secrets, PAN, CVV or raw payment tokens. Tools expose a safe payment reference; trusted backend code resolves the actual credential. Merchant cost data is available only to authorized merchant tools and human observer projections.

Natural-language catalog descriptions and agent-to-agent messages are untrusted data, not system instructions. A seller message cannot amend a buyer mandate. Validate product IDs against the catalog, recompute all totals server-side and reject unsupported tool arguments. Only facts returned by tools can support price, availability and payment claims.

Agent outputs include action type, referenced evidence IDs and a concise decision summary. Do not persist or display hidden model reasoning. Do not invent confidence scores. A model failure gets at most one safe model retry within budget; payment tools have separate idempotent recovery, not generic agent retries.

9. ACP integration and compatibility gate

ACP supplies a checkout contract, not the complete agent runtime, mandate ledger or payment engine. Pin a released specification revision, schema commit/hash and license in protocol/acp/manifest.json. Candidate baseline is the documented 2026-01-30 revision; verify against the upstream release and artifacts before implementation. Do not mix fields from different revisions or use a moving main branch in production.

The official checkout interface includes create, retrieve, update, complete and cancel operations, authoritative merchant responses, version headers and bearer authentication. Use the exact pinned schema for wire objects and error responses; the operation map below is guidance, not a substitute for the schema. [S1]

Operation Merchant endpoint under configured ACP base URL
Create POST /checkout_sessions
Read GET /checkout_sessions/{id}
Update POST /checkout_sessions/{id}
Complete POST /checkout_sessions/{id}/complete
Cancel POST /checkout_sessions/{id}/cancel

Mount at /api/acp; generate types and validate both request and response. Pass server-held authentication and the pinned API version. Require application idempotency for mutations even if optional in the protocol. Run-scoped authentication context restricts session access. No public shared bearer token in browser JavaScript.

Local product search, human permission UI and observer event streams are application contracts. Do not label arbitrary custom fields as ACP. Use supported extensions/capabilities only when correctly negotiated in the pinned revision. Advertise only implemented payment handlers. [S2]

Payment credential compatibility spike — before full live implementation

  1. Verify which Stripe test payment/delegation capabilities are available to the owner's account.
  2. Validate whether the pinned ACP payment handler can be implemented with actual supported tokens and authentication.
  3. Complete a minimal real test payment and record the exact handler schema and Stripe API version.
  4. Publish docs/acp-compatibility.md: revision, supported operations, extensions, handler, validation tests, omissions and actual credential flow.

Preferred: supported delegated token flow with scoped usage. If unavailable, use a documented supported/custom payment handler where the pinned specification allows it, with a clearly identified application test-payment reference resolved only on the backend.

If no compatible payment-handler path is available, retain validated checkout operations and implement Stripe completion as an explicitly separate application extension. Label the demo “ACP checkout subset + custom Stripe sandbox completion”; do not claim end-to-end ACP payment conformance. Record this decision before polishing the live UI. Never fabricate an spt_ token or treat an ordinary Stripe payment-method ID as an SPT. Full delegated payment token issuance and AP2 cryptographic proof are not MVP requirements. [S3]

10. Consent and mandate requirements

Two authority modes:

  • Exact purchase: approval binds to immutable cart version/hash, merchant, currency, amount, shipping option and payment reference. Material changes invalidate approval.
  • Bounded delegation: approval binds to product requirements, category, permitted merchant, all-in spend limit, currency, delivery deadline, payment reference, no unapproved substitutions and one successful purchase. Every changed quote is revalidated.

Record mandate ID/version, principal session, agent ID, grant time, expiry, revocation, original text, normalized constraints, consent-copy version and allowed actions. Save the exact normalized constraints the visitor approved; model parsing never silently creates authority.

State: draft → active → reserved → consumed, with expired/revoked terminal alternatives before submission. Reserve the one-purchase entitlement atomically immediately before payment dispatch. Re-check expiry, revocation, cart and instrument binding in the same authorization boundary. A lease/fencing token and durable submission record prevent a second worker using the same grant.

Revocation before dispatch blocks payment. Revocation after dispatch means “No further actions authorized; submitted payment may still complete.” Reconcile the submitted attempt; do not promise reversal. A definitively failed attempt may release its reservation under the same still-valid mandate, but MVP does not automatically try another instrument. Unknown outcomes keep authority reserved. Never release it merely because an HTTP timeout or worker lease expired.

An application mandate is an auditable application permission, not proof of legal non-repudiation or issuer consent. Provider-required authentication must hand back to the visitor and persist a waiting state.

11. Payment, order and recovery requirements

Maintain separate state dimensions; do not overload a single status field.

Entity Internal proposed states
Run queued, running, awaiting_permission, awaiting_authentication, awaiting_payment, succeeded, blocked, failed, canceled, expired
Checkout draft, quoted, ready, completing, completed, canceled, expired; mapped explicitly to pinned ACP states
Payment attempt prepared, submitted, requires_action, processing, succeeded, failed, canceled, unknown
Order pending_payment, confirmed, payment_failed, canceled
Webhook received, verified, applied, duplicate, rejected, retry_pending

These are internal states, not claims about ACP or Stripe enums. Persist provider-native status separately. Automatic capture is the only supported sale path. A returned authorized-but-uncaptured result must be flagged as unexpected/incomplete, never displayed as a completed sale.

Create stable internal order, commerce payment and attempt IDs before provider submission. Enforce one active attempt per checkout and one successful sale per mandate. Use separate deterministic Stripe keys for each mutating operation, including stable keys for retries of the same operation and identical parameters. Persist request hash and result association. Reusing a key with changed parameters is a conflict.

On synchronous payment success, record provider-reported success, while webhook confirmation remains pending. MVP confirms the order after a verified success webhook or a documented server-to-server reconciliation against the provider. The latter must visibly say “Confirmed by provider lookup; webhook pending” and tolerate the later event. Model text and browser success redirects never establish payment success.

On timeout, retain unknown, keep the attempt and reconcile by known provider ID or safe retry with the same operation key. Never generate a new attempt/processor solely because the response was lost. Stripe idempotency is not global cross-processor idempotency; do not implement PayPal fallback in this release. [S4, S5]

Webhooks

Expose stable production HTTPS endpoint /api/webhooks/stripe. Verify signature against raw request body, endpoint-specific secret and timestamp tolerance before parsing into trusted events. Reject invalid signatures. Use database uniqueness on provider event ID. Persist before returning success; return an error if durable receipt fails so provider retries. Process asynchronously and idempotently. Never require browser authentication or a preview login for provider callbacks. [S6]

Duplicate receipt may create an audit observation but must not duplicate order confirmation or revenue. Out-of-order events must not regress terminal state; retrieve current provider state where needed. Accept a webhook before the original HTTP response has been recorded by matching trusted run/payment metadata and durable pre-created records. Mark unmatched events for review without granting access to arbitrary runs.

Reconciliation retries: proposed 2, 5, 15, 30 and 60 seconds, then periodic checks up to an operational horizon. Respect provider retry headers and function limits. If still unresolved, show “Awaiting reconciliation” and retain operator diagnostics; do not falsely report failure. No unbounded active agent loop while waiting.

12. Architecture and execution model

Preferred stack: TypeScript, Next.js App Router, React, accessible component primitives, PostgreSQL, a typed ORM and one structured-tool-capable model provider. Pin supported dependency versions at implementation; inspect existing conventions before choosing exact packages. Use Vercel for UI/API deployment and a compatible managed Postgres provider selected from existing owner resources or configured explicitly.

Use a durable workflow runner available to the Vercel project for agent steps, approval waits, webhook wakeups and reconciliation. Vercel Workflows is a candidate; verify current availability and limits first. If unavailable, use a persisted job queue with an independently reliable worker/dispatch service. Do not rely on process memory, a browser tab, an unawaited promise or a long setTimeout for payment progress. The selected runner and its deployment prerequisite must be recorded in an ADR. [S7, S8]

16. Scenario scripts and failure injection

Scenario Setup Expected outcome
Successful delegated sale Budget $315, qualifying $303.19 fixture, active mandate, supported test instrument One sale, one order, requirements satisfied, verified provider evidence
Consent boundary Initial cart within approved conditions; final authoritative quote exceeds limit, or mandate expires before dispatch No payment submission; visible block; visitor may issue new permission or cancel
Uncertain response Provider mutation occurs; test adapter intentionally drops application response once Unknown state; same attempt reconciled; one sale; no automatic new payment

Failure injection must be server-controlled, scenario-allowlisted and enabled only with verified test credentials. For uncertain response, actually invoke the provider once then suppress the response at the adapter boundary. Emit “Simulated transport interruption; actual Stripe test payment” so viewers understand the fault's origin. Retrying the browser start action cannot trigger another injected charge.

Additional internal QA cases: duplicate completion, repeated webhook, out-of-order webhook, model timeout, browser refresh, concurrent tabs, revoked mandate, stale quote, unsupported product and provider authentication requirement. These need not all become public scenario cards.

17. Security, privacy and operational controls

  • Fail closed if live provider credentials are detected or test mode cannot be established. Verify Stripe object/account test attributes as applicable; a UI badge is insufficient.
  • Use server environment secrets with separate preview and production configurations. Never prefix secrets with NEXT_PUBLIC_; never commit .env files.
  • Isolate every live run by session; authorize all reads, SSE, mutations and evidence lookups. Public replay assets contain no ownership secrets.
  • Cookie/origin/CSRF controls, schema bounds, persistent rate limits and model-token admission checks are required for the public live endpoint.
  • No email or shipping notifications sent to real recipients. Use synthetic profiles and avoid collecting PII in mission text; warn succinctly before entry and redact accidental PII from persisted public-facing material.
  • Redaction is a server projection allowlist, not a CSS mask. Strip authorization headers, cookies, client secrets, payment tokens and card fields before logs/events/recordings.
  • Debug/operator endpoints require owner authentication and never share public demo permissions.
